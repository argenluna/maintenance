**근거 (문서 + 실측)**

| 볼륨 종류 | Windows 기본 동작 (`Optimize-Volume` 문서) |
|---|---|

| SSD + TRIM | `-Retrim` |
| Storage Space(**thin**) | `-Analyze -SlabConsolidate -Retrim` |
| SSD(TRIM 미지원), 이동식 FAT, Unknown | 동작 없음 |

### 10.4 SysFix 시간 동기화 버그 2건 (2026-11-06, 실측으로 발견)

**(1) 서비스 중지를 "정상"으로 오인**
SysFix `(3) 시간 동기화` 는 `w32tm /query /source` 결과가 `Local CMOS Clock` 인지만 봤다.
그런데 W32Time 서비스가 멈춰 있으면 이 명령은 `오류가 발생했습니다... (0x80070426)` 같은 **오류 문자열**을
돌려주고, 예전 코드는 그것을 "NTP 소스"로 보고 `PASS - 시간 동기화 정상` 을 기록했다(실측 재현).
→ 서비스를 **먼저 시작**하고, 소스가 `Local CMOS Clock`/`Free-running`/**오류 문자열**이면 재구성하도록 수정.

**(2) `w32tm /unregister` + `/register` 가 서비스 등록을 제거**
재구성 분기에 있던 `/unregister` 는 이름 그대로 **서비스 등록 자체를 삭제**한다. 이어지는 `/register` 가
되살리긴 하지만 **StartType 이 Manual/Stopped** 로 돌아오고, 자동 유지보수가 매번 이 조합을 실행하면
시간 동기화가 조용히 죽는다. 실제로 검증 중 `Get-Service w32time` 이 `NULL`(서비스 없음)이 되어
`sc query w32time` → `1060: 지정된 서비스가 설치된 서비스로 존재하지 않습니다` 를 확인했다.
→ **`/unregister` 는 코드에서 완전히 제거**. 서비스가 아예 없을 때만 `/register`(복구 등록) + `StartupType Automatic`,
그 외에는 `/config` + `Start-Service` + `/resync /rediscover` 만 사용한다.

복구 결과(실측): `w32time` = **Running / Automatic**, 소스 = **`kr.pool.ntp.org,0x9`**,
동기화 상태 4(동기화됨), 위상 오차 **-23ms**. 서비스를 일부러 중지하고 실행해도
`FIX: W32Time 서비스 시작`, `FIX: 시간 동기화 소스 재구성 (Local CMOS → kr.pool.ntp.org,0x9)` 이 기록되고
서비스가 그대로 살아 있는 것을 확인했다.

**교훈**: 시간 동기화 계열 명령은 "되돌릴 수 있다"고 가정하면 안 된다. `/unregister` 처럼 **등록을 지우는**
명령은 자동화에서 배제하고, 재구성은 설정(`/config`)과 재동기화(`/resync /rediscover`)만으로 수행한다.

### 12.7 검증 중 발견한 기존 버그 2건 — 출력 리다이렉션 시 한글화 (2026-11-10)

광고 단계 검증에서 "왜 `Recovery` 가 계속 FAIL 인가"를 파고들다 **광고와 무관한 기존 버그 2개**를 찾았다.
원인은 같다: **native 도구(`reagentc`, `winmgmt`)는 콘솔에 직접 쓸 때는 영문으로 출력하지만,
stdout 이 파일/파이프로 리다이렉션되면 OS 표시 언어(한글)로 출력**한다. 스크립트는 영문 라벨만 매칭했다.

| 단계 | 증상 | 원인 (실측 출력) | 수정 |
|------|------|------------------|------|
| `Recovery` | 예약 작업/래퍼 실행에서 **항상 FAIL** (대화형 실행에서는 PASS) | `Windows RE 상태: Enabled` — `Windows RE status:` 불일치 | `^\s*Windows RE[^:\r\n]*:\s*Enabled` (값 `Enabled` 는 로캘 무관), BCD 도 `^\s*BCD[^:\r\n]*:\s*0{8}-` |
| `WMI` | **항상 SKIP(판정 불가)** — 손상 여부를 아예 못 봄 | `WMI 리포지토리가 일관적입니다.` — `WMI repository is consistent` 불일치 | 영문+한글 동시 매칭. **부정(불일치)을 먼저** 검사(`일관적이지` ⊃ `일관적`) |

**검증**: 수정 후 `run-maintenance.ps1 -Force`(stdout 파일 리다이렉션 = 예약 작업과 동일 조건)

PS 7 · PS 5.1 파서 검사 오류 0.

교훈: **native 도구 출력을 파싱할 때는 실행 컨텍스트(콘솔/리다이렉션)에 따라 언어가 바뀐다는 점**을 전제로

같은 함정이 다른 속성에도 있을 수 있으니, CIM/NetAdapter 속성에 `.ToString(포맷)` 을 쓸 때는 타입을 먼저 확인할 것.

**검증**: `run-maintenance.ps1 -Force` 38.6초, PASS, stderr 없음, 메트릭 변경 없음(0/1/2 유지),
`status=PASS`, `[광고 설정 주의]`·`Ad Warnings` 1회씩 유지.

### 12.9 삭제 전 확인 — 지우기 전에 목록 + y/N, 결과 txt 기록 (2026-11-12)

사용자 요청: **"자료를 지우기 전에 지우려는 목록을 보여주고 yes/no 를 고르게 해달라"**,
그리고 **"그 지우는 목록도 나중에 결과 txt 파일에 표기해달라."**

기존에는 휴지통·브라우저 캐시·임시폴더·지난 리포트를 **묻지 않고** 지웠다. 컴맹 사용자 입장에서
"내 파일이 사라졌는데 왜 그런지 모른다"가 가장 위험한 실패 모드이므로, 삭제를 **검토(review) 단계**로 감쌌다.

**설계 원칙 — "물어볼 사람이 없으면 지우지 않는다"** (2026-11-12 2차 지시로 더 강화)

| 실행 경로 | 동작 |
|-----------|------|
| 바탕화면 "지금 점검"(`run-maintenance.ps1 -Force`) · 설치 첫 점검 · 콘솔 `-Mode check` | 목록 + 남은 용량 + 백업 안내 → `삭제하시겠습니까? (y/N)` → **`y` 일 때만 삭제** |
| 예약 실행(`-Mode scheduled` / `idle`, 물어볼 사람 없음) | **아무것도 지우지 않고 "보류"** 로 기록 |
| 어떤 경로든 | 자동 삭제 경로 **없음** (`deleteConfirm` 설정 제거) |

> 2차 지시(2026-11-12): "용량이 적게 남았더라도(극단적으로 100MB 라도) 최소 용량 확보를 위해 자동 삭제하지 마라.

> 라고 물어보고 y 를 눌러야만 지워라." → `auto` 결정 경로를 삭제하고, 디스크 부족 시에도 목록만 만든다.

- `run-maintenance.ps1` 은 `-Force`(사용자가 직접 누른 경우)에만 `-PromptForDelete` 를 넘긴다.
  예약 작업은 `-Mode scheduled` 만 넘기므로 구조적으로 "자동 삭제" 경로가 없다.
- 보류된 항목은 `recommendations` 에 `[삭제 보류] … "지금 점검"을 실행하면 물어봅니다` 로 남는다.

**공통 헬퍼 `Invoke-DeleteReview`** — 삭제 지점 4곳을 모두 이 함수로 통일했다.

| 대상 | 조건 | 이전 |
|------|------|------|
| 휴지통 (`Shell.Application` 0xa) | 30일 이상 지난 항목 | 즉시 `InvokeVerb('delete')` |
| 브라우저 캐시 (Chrome/Edge/Brave) | 30일 이상 지난 파일 | 즉시 `Remove-Item` |
| 임시 폴더 (`tempDirs`) | 디스크가 `diskThresholdGB` 미만일 때 | 즉시 `Remove-Item` |
| 바탕화면 지난 결과 파일 (`자동유지보수_*.txt`, `MaintenanceReport_*.txt`) | 7일 이상 | 즉시 `Remove-Item` |

목록 표시: 큰 파일부터 **20개**(나머지는 `... 외 N개`) + 총 개수/용량. 항목 형식 `이름 (용량, yyyy-MM-dd)`.

```

**기록 3곳** (사용자 요청 두 번째 항목)

1. 로그 `Delete Review:` 줄 + `    · 파일` 목록
2. `last-result.json` → `deleteReview` (`target/count/size/decision/decisionText/shown/more`)
3. 데스크톱 결과 txt → `[삭제 전 확인 목록 — 파일을 지우기 전에 보여준 목록]` (상위 10개 + `... 외 N개`)

`decision` 은 `yes`(사용자가 y 선택) / `no`(사용자가 아니오) / `deferred`(자동 실행 — 보류).
`auto`(설정으로 확인을 끄는 경로)는 2026-11-12 2차 지시로 **제거**했다.

**부수 수정**: 지난 결과 파일 정리를 **리포트 작성 단계 앞으로 이동**했다. 뒤에 있으면
(a) 이번 실행의 삭제 목록이 이번 리포트에 안 들어가고 (b) 방금 만든 리포트와 섞여 헷갈린다.

**검증 — 단위 테스트(PowerShell 5.1, `Read-Host` 스텁) ALL PASS**

### 12.10 【사고】 배포본이 사용자 사진을 삭제 — 원인 분석과 4중 안전장치 (2026-11-12)

**보고**: "어제 친구한테 배포했는데 I: 드라이브에 저장해둔 사진 자료를 멋대로 지우기 시작했다.
SSD 500GB에 24GB 남았는데 막 지우기 시작했다."

**결론: 코드 버그다.** `%TEMP%` 가 가리키는 폴더를 "임시 폴더"라고 믿고 `-Recurse` 로 전부 지우는
코드였고, 확인·나이제한·경로검증이 전부 없었다. 배포본(2026-11-11 22:29 zip = HEAD `0df9808`)으로
사고를 **그대로 재현**해 확인했다.

#### 사고 체인 (4단계)

| # | 단계 | 코드/동작 | 결함 |
|---|------|-----------|------|
| 1 | 트리거 | `foreach ($d in Get-PSDrive ...) { if ($freeGB -lt $diskThreshold) { ...정리... } }` | **어느 드라이브든** 10GB 미만이면 실행. 24GB 남은 SSD와 무관한 드라이브(작은 파티션·USB·카드리더·가상드라이브)가 원인이 될 수 있음 |
| 2 | 대상 | `$tempDirs = Get-Cfg 'tempDirs'` (기본 `@("$env:TEMP", "$env:windir\Temp")`) | 사용자 PC의 `TEMP`/`TMP` 가 `I:\`(또는 I: 내 폴더)를 가리키면 **그 드라이브가 대상이 됨**. `TEMP` 를 다른 드라이브로 옮기는 건 흔한 설정 |
| 3 | 삭제 | `Get-ChildItem -Path $td -Recurse -File` → `$items \| Remove-Item -Force` | 드라이브 루트 검사 ✗, 확장자/폴더 검사 ✗, 나이 제한 ✗, 용량 상한 ✗, **확인 프롬프트 ✗**(배포본에는 기능 자체가 없음) |
| 4 | 기록 | `$remaining` 이 비면 `(…).Sum` 에서 StrictMode 예외 → `catch` → `Error during cleanup` | 결과 txt·`autoFixes` 에 **무엇을 지웠는지 안 남음** → 사용자에게는 "멋대로 사라진" 것으로 보임 |

#### 재현 (배포본 그대로, `Z:\` 샌드박스에 사진/문서/영상 배치)

| 빌드 | 프롬프트 | 결과 |
|------|----------|------|
| **배포본(HEAD)** | **0건** | 파일 5개(오늘 찍은 사진 포함) **전부 삭제**, 빈 폴더만 남음, 로그는 `Error during cleanup` 뿐 |
| 수정본 1차(삭제 전 확인) | y/N 표시 | 사용자가 `y` 를 누르면 여전히 전부 삭제 → **불충분** |
| **수정본 최종** | y/N + 가드 | 5개 **전부 보존**, `[정리 제외] … 사진/문서 폴더로 의심됨` 기록 |

#### 수정 내용 — 임시 폴더 정리 4중 안전장치

1. **경로 검사** `Test-SafeTempDir`
   - 드라이브 루트(`I:\`) **무조건 금지**
   - 바탕화면·문서·사진·비디오·음악·다운로드·OneDrive·Dropbox·Google Drive·설치 폴더 금지
   - 이름이 임시 폴더가 아니면 제외 (`Temp`/`Tmp`/`Cache`/`AppData\Local\Temp`/`Windows\Temp` 만 허용, config 에 직접 적은 경로는 이름 규칙 완화)
   - `SystemDrive('C:')` 는 보호목록에서 제외 — 넣으면 `C:\Temp` 같은 정상 경로까지 거부된다(단위테스트에서 발견)
2. **드라이브 일치** — 부족한 **그 드라이브** 안의 임시 폴더만 정리. USB/작은 파티션 때문에 `C:\Windows\Temp` 나 `I:\…` 를 건드리지 않는다.
3. **나이 제한** `tempMinAgeDays`(기본 1일) — 최근 파일은 후보에서 제외.
4. **용량 상한** `tempCleanupMaxGB`(기본 5GB) — **목표 용량까지 채우려고 추가 삭제하지 않는다**(여유 공간은 기록만).
5. 보조: 제외된 경로는 `[정리 제외] '경로' — 이유` 로 결과 txt 에 남긴다. `TEMP` 가 드라이브 루트인 PC는 자동 정리를 건너뛰고 그 사실을 알린다.
6. 보조: `Get-FilesNoReparse` — 임시 폴더 안의 **정션/심볼릭 링크 디렉터리는 따라가지 않는다**.
   `Get-ChildItem -Recurse` 가 링크를 따라가면 링크 대상(사진 폴더 등)의 실제 파일까지 목록에 들어가 삭제될 수 있다.

#### 검증

- `Test-SafeTempDir` 단위테스트 **15/15 PASS**
  (`Z:\` 거부, 사진 폴더 거부, `I:\code\maintenance` 거부, `C:\Temp`/`D:\Temp`/`AppData\Local\Temp`/`Windows\Temp` 허용,
   explicit 이어도 루트·사진 폴더는 거부)
- E2E: `TEMP`=사진 폴더 + 디스크 부족 → **5개 보존**, `Cleanup: SKIP - 안전 가드` + `[정리 제외]` 기록
- E2E: `TEMP`=`…\Temp`(2024 파일 2개 + 오늘 파일 1개) → **2024 파일만** 목록에 오르고 삭제, **오늘 파일 보존**
  (결과 txt 에 `[임시 폴더 (…)] 2개 / 3.0MB → 지움 (사용자 확인)`, `Cleanup: Removed 3.0MB (남은 1개 … — 최근·사용 중 파일은 유지)`)
- 정션 테스트: `Temp\link → photos`(사진 1개) + `Temp\old.log` → `Get-FilesNoReparse` 는 **old.log 1개만** 반환(링크 내부 제외)
- PS 5.1 파서 오류 0

#### 교훈

- **"설정값이 가리키는 경로"를 검증 없이 재귀 삭제하면 안 된다.** `%TEMP%` 는 사용자가 얼마든지 바꾸는 값이고,
  드라이브 루트일 수도 있다(이 개발 PC도 `TEMP=Z:\`).
- **삭제 트리거와 삭제 대상을 분리해서 검사해야 한다.** "어떤 드라이브가 부족하다"와 "어느 폴더를 지운다"는
  별개 문제인데, 기존 코드는 전자를 후자의 근거로 삼았다.
- **삭제 실패/예외가 삭제 기록을 덮으면 안 된다.** 4단계 버그 때문에 사용자는 무엇이 지워졌는지조차 볼 수 없었다.

사용자 지시: **"삭제하려는 파일 경로와 폴더 및 파일 이름은 남아있지? 결과 txt에도 남아있어야 하고.

|------|------|------|

### 12.13 "부족" 기준 = 각 드라이브 용량의 10%, 경고는 정말 위험할 때만 (2026-11-13 5차 지시)

사용자 지시: **"아니... 500GB 남고 3TB 남았는데 몇 GB 남았습니다. 문제가 생길 수 있습니다. 띄우는 게 말이 되냐?
이 정도 남으면 문제가 생길 수 있다. 라고 적정한 용량 이하로 남았을 때 그런 경고가 나와야지...

**문제**: 12.11 에서 넣은 경고가 *설정값만* 보고 판단해서, `diskThresholdGB` 가 큰 값(테스트의 999999,
사용자 실수)이면 **1.1TB 남은 드라이브에도** `여유 공간이 1134.92GB 밖에 없습니다. 현재 용량으로는 디스크

| 항목 | 이전 | 이후 |
|------|------|------|
| 부족 판정 기준 | `diskThresholdGB` 절대값(기본 10GB) | **그 드라이브 용량의 10%** (1.86TB → 186GB, 4TB → 400GB, 64GB → 6.4GB) |
| `diskThresholdGB` | 판정 기준 그 자체 | **용량을 알 수 없는 드라이브의 대체값**으로만 사용 |
| "문제가 있을 수 있습니다" 경고 | 기준 미만이면 무조건 | **5GB 미만**(소형 드라이브는 용량의 5%)일 때만 |
| 기준 미만 문구 | `N GB 밖에 없습니다 + 문제가 있을 수 있습니다` | 5GB 이상이면 `N GB 입니다 + 백업 후 X GB 확보 권장` (위험 경고 없음) |
| 임시 폴더 프롬프트 | 항상 4줄(여유/문제/삭제/백업) | 5GB 미만이면 4줄 그대로, 그 이상이면 `여유 공간을 조금 확보하려고 오래된 임시 파일부터 정리하려고 합니다` + 백업 안내 |

- 판정은 `Free + Used`(PSDrive) 로 그 드라이브의 실제 용량을 구해 10% 를 계산한다. 용량을 못 구하면 설정값.

**검증**

  4GB/1TB·1GB/500GB·100MB/500GB → 경고, 64GB 드라이브는 5%(3.2GB) 기준, 용량 미상은 5GB 기준.
- E2E 3회(배포본):
  1. 기본 설정 → **Disk 권고 0건 · 삭제 프롬프트 0건** (모든 드라이브가 10% 이상 남아 있음).
  2. 임계값 강제(10배) → C 1134GB·D 470GB 에 대해 `밖에 없습니다`/`문제가 있을 수 있습니다` 없이

  3. 위험 수준 강제(100MB 상황과 동일) → notice 4줄 그대로(여유 공간 / 문제가 있을 수 있습니다 /
     오래된 파일부터 삭제 / 백업 안내), 결과 txt 에도 동일.

원인은 SFC 로그가 기호로 찍히고 있었기 때문:

```

SFC 복구: ✓ 완료 / SFC 복구: ✗ 실패
DISM: ✓ 구성 요소 저장소 손상 없음

결과 txt 필터가 `^\w.*: (PASS|FAIL|WARN|CHANGE)` 만 통과시키므로(§12.16에서 상세 줄 예외만 추가),

→ `SFC: PASS - 문제 없음`, `SFC: WARN - 시스템 파일 무결성 위반 발견, 복구 시도 중...`,

### 12.18 반복 크래시 앱의 정체를 알려준다 — v1.1.3 (2026-11-16)

| 이름 | 실제 제품 | 비고 |
|------|-----------|------|
| `grap-core64.aes`, `grap64.dll`, `BlackCipher64` | Nexon Game Security (NGS) | 메이플스토리·블루아카이브 등 넥슨 게임 안티치트. 게임 종료 후 잔여 프로세스가 남아 크래시 기록을 쌓는 경우가 흔하다 |

**수정**

1. `Get-KnownSecurityProduct` 추가 — 이름을 제품명 + 설명 + 실제 조치로 바꾼다.
   `grap-core64.aes` → `Nexon Game Security (NGS, 구 BlackCipher) — 메이플스토리·블루아카이브 등 넥슨 게임 안티치트.
   게임과 런처를 완전히 종료(트레이 아이콘까지)하면 사라집니다. 게임을 끈 상태에서도 반복되면 게임 파일 무결성 검사/재설치`.
   대응: NGS / Vanguard / Tencent ACE / XignCode3 / nProtect GameGuard / Easy Anti-Cheat / BattlEye.
   **정확한 이름만 매칭**한다(오탐으로 엉뚱한 제품명을 알려주면 더 나쁘다). `WLANExt.exe`, `explorer.exe`, `chrome.exe` 는 해당 없음으로 확인.
2. 반복 크래시 WARN 문구도 바꾼다: `— 앱/드라이버 업데이트 필요` → `— <제품명> — <설명>`.

#### ① 결과 파일이 4개 이상 → `자동점검결과` 폴더로 이동

**구현** — `maintenance.ps1` 에 `Move-OldDesktopReports` 추가.

- 리포트를 쓰기 **전에** 호출한다(이번에 만들 파일까지 합쳐 4개 이상이면 동작). 그래야
  (a) 이번 리포트 요약에 정리 내역이 들어가고 (b) 방금 만든 파일이 폴더로 들어가지 않는다.
- 기존 파일을 최신순으로 정렬해 **가장 최근 1개만 남기고** 나머지를 `자동점검결과` 폴더로 **이동**한다.
  - 지우지 않는다(안전·가역). 폴더가 없으면 만든다.
  - 폴더 자리에 같은 이름의 **파일**이 있으면 아무것도 하지 않고 로그에만 남긴다(안전).
  - 같은 분(minute)에 두 번 실행해 대상 폴더에 같은 이름이 있으면 `_yyyyMMdd_HHmmss` 를 붙여 덮어쓰지 않는다.
- 결과 txt 요약에 `[바탕화면 정리]` 절, 로그에 `REPORT: CHANGE - 이전 결과 파일 N개를 '자동점검결과' 폴더로 옮김`
  + 옮긴 **전체 경로**를 한 줄씩 남긴다.
- 기존 "7일 이상 지난 결과 파일" 삭제 후보 검색을 **바탕화면 + `자동점검결과` 폴더** 두 곳으로 넓혔다
  (옮긴 파일도 결국 같은 규칙으로 정리된다). 이 검색은 `-ReportTo`(사용자 바탕화면) 를 쓰도록 통일했다
  — 이전에는 `[Environment]::GetFolderPath('Desktop')` 를 직접 읽어 관리자 계정 바탕화면을 볼 수 있었다.
- `run-now.ps1` / `install.ps1` 의 "최신 리포트 찾기"도 두 위치를 함께 보고 **더 최신 파일**을 고른다
  (폴더로 옮겨져도 결과 창이 열린다).

#### ② 자동 실행 콘솔: 유휴 = 창 보임 / 사용 중 = 헤드리스

기존에는 자동 실행이면 무조건 창을 숨겼다(`scheduled`). 이제 `run-maintenance.ps1` 이 **한 곳에서** 판정한다.

| 상황 | 콘솔 | 근거 |
|------|------|------|
| 직접 실행(`-Force`, "지금 점검"·설치 첫 점검) | 보임(같은 창, `-NoNewWindow`) | `-NoHideConsole` 전달 |
| 자동 + 유휴(`idleConsoleMinutes` 이상 입력 없음, 기본 5분) | **새 창 보임** | `Start-Process` 기본값 = 새 콘솔 |
| 자동 + 사용 중 | **창 없음(헤드리스)** | `ProcessStartInfo.CreateNoWindow = $true` |

- 유휴 판정: `System.Windows.Forms.SystemInformation.IdleTime` (기존 `Get-IdleTimeSeconds` 와 동일 소스).
  설정 키 `idleConsoleMinutes` — `0` = 항상 보이게, `N` = N분 이상 유휴면 보이게. 없으면 5.
- **실측으로 바꾼 부분**: 예약 작업은 `-WindowStyle Hidden` 으로 래퍼를 띄우는데,
  `Start-Process -NoNewWindow` 는 부모의 숨김 콘솔을 물려받는 것처럼 보이지만 **자식에게 새 콘솔 창이 생겼다**
  (자식이 자기 창을 검사: `hwnd=2231728 visible=True`). 즉 "사용 중"에도 창이 잠깐 깜빡였다.
  `CreateNoWindow` 는 창 핸들 자체가 `0` 이라 깜빡임이 없다(자식 실측 `hwnd=0 visible=nohwnd`).
- 헤드리스는 표준출력/표준에러를 `logs\console-yyyy-MM.log` 로 받는다(교착 방지: stderr 는 비동기로 읽음).
  종료 코드는 두 방식 모두 정상 수집(실측 exit 7/5/0).
- `maintenance.ps1` 은 판정하지 않고 지시만 받는다(`-NoHideConsole` / `-HideConsole`).
  옛 `-Mode idle` 직접 실행처럼 지시가 없으면 `idleConsoleMinutes` 로 스스로 판단한다(유휴면 창 보임).
  이렇게 한 곳에서만 판정해, 2026-11-14 의 "양쪽이 따로 판정해 창이 사라지던" 사고를 막는다.

#### ① 최신 것까지 전부 `자동점검결과` 폴더로 이동

- 이전(v1.3.0): 기존 파일 중 **최신 1개는 바탕화면에 남기고** 나머지만 폴더로 이동 → 바탕화면에 결과 2개(기존 최신 + 이번 것).
- 변경(v1.4.0): `Move-OldDesktopReports` 가 **기존 파일 전부**를 폴더로 이동 → 바탕화면에는 **이번에 새로 만든 1개만** 남는다.
- 이름이 같은 파일이 폴더에 이미 있으면(`_yyyyMMdd_HHmmss` 접미사) 덮어쓰지 않는다(기존 동작 유지).
- 정리 시점을 **요약 단계 앞**으로 옮겼다. `last-result.json`(`desktopReportMove`)과 결과 txt `[바탕화면 정리]` 절,
  콘솔 `[정리] …` 줄에 같은 내역이 남는다(이전에는 리포트 생성부에서만 이동해 JSON 에 기록되지 않았다).
