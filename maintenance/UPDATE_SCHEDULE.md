# 자동 유지보수 업데이트 — 주간 예약표

> 작성: 2026-11-21. 이 파일은 **배포 슬롯 운영표**다. `feedback-token.txt` 와 달리 민감정보가 없으므로 커밋해도 된다.

## 운영 규칙 (사용자 확정)

1. **배포는 주 1회(토요일 04:00).** 슬롯은 미리 한 주씩 예약해 둔다.
2. **배정 순위 (사용자 확정, 2026-11-22):** 내가 정한 것 > Win11 > Win10 > Win7 > 기타.
   - "내가 정한 것" = 심사로 확정한 패치 순서. **이 순서대로 슬롯을 채운다.**
   - OS 티어(Win11 > Win10 > Win7 > 기타)는 내가 정한 항목들 **뒤**의 정렬 기준일 뿐, 앞순위를 밀어내지 못한다.
   - 추후 내가 "이거 패치해야 할 것 같다"고 하면 **그걸 맨 앞으로 배정**하고 기존 건들은 뒤로 밀린다.
3. **슬롯당 최대 5개.** 5개가 넘으면 다음 슬롯을 계속 만들어 넣는다. (기존 4개 슬롯에 갇히지 않음) — 2026-11-22 사용자 확정: 배치당 검증 부담과 관련 조치 묶음을 고려해 10개에서 5개로 줄임. 이후 슬롯은 로컬 전용 일정표에서 관리.
4. **만료 없는 피드백 토큰의 배포 묶음은 로컬 전용 일정에서 관리한다.** (공개 표에는 다음 주 슬롯만 기재)
   - 만료일이 있는 토큰은 넣지 않는다.
5. 버전 번호는 슬롯 순서대로 1개씩 올린다.
   - **표기는 `v 1.17.00` 형식(major 그대로, minor·patch 두 자리, `v` 뒤 공백)으로 통일한다.** github 릴리스 태그는 공백을 쓸 수 없어 `v1.17.00` / `v1.17.00-rcN` 으로 올린다.
   - 현재 최신 배포: **v1.16.0** (2026-11-21 우선처리 조기 배포). `VERSION` 의 `1.17.01` 은 W1 구현 버전이며, 배포 태그(`v1.17.01`)와 일치한다.
   - **공개 표에는 다음 주 슬롯(W1=`v 1.17.01`, 2026-11-28)만 기재**한다. 그 이후 슬롯(구 W2~W6)과 오늘 정리한 검출기·편의성 계획은 **로컬 전용 일정표**(`maintenance/research/next/_schedule_full_local.md`, `_plan_w7_plus.md`)에서 관리하며 GH에는 올리지 않는다.
   - 같은 날 Replay 감시 항목은 **코드 찌꺼기 수정**으로 분류해 슬롯을 기다리지 않고 **즉시 패치**했다. 스크립트·예약 작업·3개월 조건은 그대로이며, 이전 설치본 `config.json` 에 남아 있던 감시 항목만 제거했다.
   - 버전 비교 로직(`update-common.ps1` 등)은 다음 버전부터 zero-padding 기준으로 정비한다. 지금은 `[version]::TryParse('1.17.00') == 1.17.0` 이므로 비교에는 영향이 없다.
   - 작업 디렉터리의 `VERSION` 은 현재 슬롯 버전(W1=`1.17.01`)을 유지하고, 실제 배포 태그도 같은 번호(`v1.17.01`)를 따른다. `PreVerify` 가 `VERSION == 태그` 를 검사하므로 두 값은 항상 일치시킨다.
   - 예외: 2026-11-21 에 "보고서 자동 업로드 + 피드백 안내 + 뉴비 보고서"가 최우선 요청으로 들어와 주간 슬롯을 기다리지 않고 **v1.14.7 로 즉시 배포**함.
   - 같은 날 "A 선택 후 예약 실행도 자동 업로드 + 업로드 원본 버그" 추가 요청으로 **v1.14.8 로 즉시 배포**함. 이후 슬롯 번호가 밀림.
   - 같은 날 "조사 결과 우선 반영 — 업데이트 실패 이력/오류 코드 해석(보고만)" 요청으로 **v1.15.0(기능 추가 = MINOR) 즉시 배포**함.
   - 같은 날 "예약 배포 1주 전 미리검증" 요청으로 **v1.15.1(동작 변경 = MINOR) 즉시 배포**함.
   - 같은 날 "피드백 개인정보 범위·다음 버전 수정 안내" 요청으로 **v1.15.2(문구 수정 = PATCH) 즉시 배포**함.
   - 같은 날 "DISM 검사 기본 + 문제 시에만 Y/N 복구" 요청으로 v 1.17.00(기능 추가 = MINOR)을 준비했으나, **사용자 요청으로 즉시 배포하지 않고 로컬 전용 일정의 `#11`에 흡수해 예약**함. 이후 추가된 "점검 끝 통합 + 첫 질문 문구" 변경도 같은 건에 합침.
6. 실제 PC 반영은 예약 작업이 수행한다.
   - `OpenCode-Maintenance-AutoUpdate-Weekly` : 매주 토 04:00 (첫 실행 11/28) — **안정본만** 설치
   - `OpenCode-Maintenance-AutoUpdate-1Month` : **비활성화** (토큰분 배포 묶음은 로컬 전용 일정에서 관리)
   - `OpenCode-Maintenance-PreVerify` : **매일 03:30** — RC 가 있을 때만 미리검증(보고만, 설치본 변경 없음)

## 3단계 검증 배포 게이트 (2026-11-21 사용자 확정)

예약일을 **D** 라고 할 때, 한 버전은 아래 3단계를 반드시 거친다.

| 단계 | 시점 | 무엇을 하느냐 | 산출물 |
|---|---|---|---|
| ① 로컬 카나리 | **D-14** | 빌드한 ZIP 을 **이 PC 에 로컬로 먼저 설치**해 실제 점검을 돌려본다.<br>문제가 있으면 이 단계에서 고친다. | 이 PC 설치<br>· 점검 결과 |
| ② RC 공개·미리검증 | **D-7** | 같은 ZIP 을 GitHub 에 `vX.Y.Z-rcN` **prerelease** 로 공개.<br>`OpenCode-Maintenance-PreVerify`(매일 03:30)가 파일/구문/BOM/VERSION/회귀 SelfTest 를 검사.<br>사용자는 안내창 아래 **미리 해보기**로 별도 폴더에서 체험 가능. | 바탕화면 `자동유지보수_미리검증결과.txt`, `H:\AutoMaintenance_PreVerify.log` |
| ③ 본배포 | **D (토 04:00)** | 같은 ZIP 을 **안정 태그 `vX.Y.Z`** 로 새로 공개 → 주간 자동업데이트가 설치.<br>RC(`vX.Y.Z-rcN`)는 prerelease 로 남겨 두어 자동업데이트가 계속 무시. | 안정 설치<br>· `배포됨` 갱신 |

- **RC 는 절대 자동 설치되지 않는다.** `vX.Y.Z-rcN` 은 `[version]` 파서가 무시하고 `prerelease=true` 도 한 번 더 걸러낸다.
- **미리 해보기는 현재 설치본을 안 바꾼다.** `H:\AutoMaintenance_Canary_<태그>` 에만 설치하고 바탕화면에 `자동유지보수 미리해보기.lnk` 를 만든다. 예약 작업·메인 바로가기는 그대로.
- **미리검증은 읽기 전용이다.** 삭제·수정·업로드 없이 결과만 보고한다. 문제가 나면 RC 를 고쳐 다시 올리고, 그 슬롯의 본배포를 미룬다.
- **검증 통과 문구**: "문제 없음 — 예약일 본배포 진행 가능" / 실패 시 "문제 발견 — N건 (본배포 보류)" + 항목별 상세.
- **업데이트 이후 할 일 (지금 하지 않음)**: 로컬 버전 안내 HTML은 `현재 기능 / 현재 기능 변경점 / 다음 버전 변경점` **원래 제목을 유지**한다. 본배포 완료 후 **GH 에 `버전 안내` 카테고리를 만들고**, 거기에 올리는 버전 안내만 `현재 기능 / 현재 기능 변경점 / 다음 버전 변경 예정점`으로 바꿔 **국문 + 영문을 함께** 게시한다. 영문 열 제목은 `Current Features / Current Version Changes / Planned Changes for Next Version`. 현재 `gh` 인증·연결이 없어 생성 불가. 편의성 패치 내역은 공개 저장소에 올리지 않는다.

### 릴리스 노트 문구 규칙 (안내창이 그대로 읽어감)

릴리스 노트의 `-` 목록이 안내창의 "기능 n가지" 목록이 된다. 채널별 첫 문구를 아래처럼 쓴다.

- **② RC(prerelease)** — `미리 다운로드 / 미리 해보기`
  ```
  미리 해보기 — 준비 중인 기능입니다.
  - 전 버전보다 N가지 기능이 추가되고, 추가된 기능은 아래와 같습니다.
  - (문제가 있으면 제작자에게 연락 주세요. 최소 로컬 컴퓨터로 검증 완료.)
  - ...실제 변경 항목...
  ```
- **③ 안정본(stable)** — `현 버전 다운로드`
  ```
  현 버전 다운로드 — 안정화된 기능입니다.
  - 추가된 기능 설명: ...
  - ...실제 변경 항목...
  ```

## 컴퓨터 초보자를 위한 기능 업데이트 내용

이번 예약은 **실제 점검 결과와 자주 들어온 문의**를 바탕으로, 컴퓨터를 잘 모르는 분도 안전하게 쓸 수 있도록 정했습니다.

- **v1.15.0 — 업데이트 실패 이유를 알려줘요**
  - 윈도우가 업데이트에 실패하며 남긴 메모를 최근 30일치 읽어, `0x80070002` 같은 숫자 코드가 무슨 뜻인지 쉬운 말로 알려줍니다.
  - 예를 들어 "필요한 파일을 못 찾았어요", "드라이버 때문에 멈췄어요"처럼 말이에요.
  - **자동으로 고치지는 않고 알려주기만 합니다.** 계속 실패하면 설정 > Windows Update > 업데이트 기록에서 직접 확인하실 수 있어요.
- **v1.15.1 — 새 기능을 미리 해볼 수 있어요**
  - 정식 배포 일주일 전에 "준비 중인 기능"을 먼저 알려드립니다.
  - 안내창 아래의 작은 **미리 해보기** 버튼을 누르면 지금 쓰고 있는 버전은 그대로 두고 새 기능만 따로 받아 체험할 수 있습니다.
  - 문제가 있으면 제작자에게 연락 주세요.
  - 매일 자동으로 미리 검사해서 결과를 바탕화면 `자동유지보수_미리검증결과.txt` 에 적어둡니다.
  - 정식 버전은 예약된 날에만 자동으로 설치됩니다.
- **v1.15.2 — 피드백 보낼 때 알려드려요**
  - 오류 확인을 위해 올라가는 내 컴퓨터 정보는 CPU 모델과 GPU 모델뿐입니다.
  - 이름·경로·시리얼·IP 같은 개인정보는 자동으로 지우고, 보고서 구분용 해시 앞 6자리만 함께 올라갑니다.
  - 보내주신 문제는 대부분 다음 버전에서 수정됩니다.

## 작업 순서 (매주 — 3단계 게이트 적용)

1. 사용자에게 받은 항목을 위 분류 기준으로 분류 → 해당 슬롯에 추가 (없으면 다음 빈 슬롯).
2. **D-14 (로컬 카나리)**: 그 슬롯 항목만 구현 → VERSION 올림 → 파서/BOM/SelfTest 검증 → 로컬 ZIP 빌드 → **이 PC 에 로컬 설치해 실제 점검**. 문제 나면 여기서 고친다.
3. **D-7 (RC 공개)**: 같은 ZIP 을 `vX.Y.Z-rcN` prerelease 로 Release.
   - 릴리스 노트는 위 "릴리스 노트 문구 규칙" 적용.
   - 매일 03:30 미리검증 로그·바탕화면 보고서 확인.
   - 원하면 **미리 해보기**로 별도 폴더에서 체험.
4. **D일 (토 04:00, 본배포)**: 미리검증이 "문제 없음"이면 같은 ZIP 을 안정 태그 `vX.Y.Z` 로 공개 → 주간 자동업데이트가 설치.
   - RC 는 그대로 남아도 `[version]` 파서가 무시하므로 자동 설치되지 않는다.
   - 문제가 나면 본배포를 미루고 RC 를 고쳐 다시 올린다.
5. 본배포 후 이 표 상태를 `배포됨` 으로 갱신.
6. 만료 없는 토큰의 배포 묶음은 로컬 전용 일정에서 확인·관리한다.
